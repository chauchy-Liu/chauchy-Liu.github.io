提示词工程

系统提示词和用户提示词，prompt是与LLM打交道的唯一方式。应用层的技术是为了拼出一个合适的promt。

  • 身份设定
  • 背景设定
  • 参考资料
  • 样例
    • 没有样例：Zero-Shot
    • 一个样例：One-Shot
    • 多个样例：Few-Shot
    • 如何动态添加样例而不是手写样例
      • RAG：Retrieval-Augmented Generation（回答问题之前先做一轮内部知识搜索）
        • 将参考资料和样例放在prompt中，就叫做In-Context-Learning（下一轮对话需要注入上下文，否则会忘掉）
        • 模型接收提示词有字数限制，且内容多性能下降，需要知识库塞入这些内容。
        • 构建知识库：
          • 分析场景是宽场景还是窄场景
          • 搜集文件（pdf、word、md、html、表格、图片）并纯文字化-》
          • 分块/切片（100～2000文字）（ai、agent、人工）-〉
            • 技巧：每一个切片是一个对立的主题（一行一个主题）
            • 技巧：人为切分固定数量的文本
            • 技巧：问答对格式，一个问答对为一个chunk，优先使用rag而不是微调
          • 向量化embedding和存储
          • 优化检索结果
            • 没有检索到
            • 检索到了但是相似度不高
        • LLM调用知识库：
          • 用户query-》向量化embedding
          • 在向量库中搜索相似的向量
          • 拼接提示词（系统提示词+搜索到的知识向量+原始query向量）=》最终提示词
          • 最终提示词给LLM并给出反馈
  • 指令
  • 限制条件

工作流和skill是提前开发好的功能模块，大语言模型有function call能力（大语言模型能够看到用户的自然语言命令、要求和问题，并有能力自主判断是否要调用某个功能模块（工具）、调用哪些功能模块、调用工具时的参数是什么），但是你要把这些可被调用的工具写到系统提示此中，否则大语言模型不知道都有哪些工具可被它支配。

大模型原理和API使用

ChatGPT如何训练出来的

  • 搜集数据，监督学习模型
  • 训练奖励模型（reward model）,对监督模型给出的文本结果使用Rank List (RLHF) 人工排序，奖励模型给监督模型对同一个问题生成的多个文本结果排序（打分），两者对比更新奖励模型
  • 训练强化模型(ppo)，将强化模型生成的文本给奖励模型，让奖励模型给结果打分

不同语言模型的token如何定义

token是大语言模型处理文本的最小单元。token被转换成一个数字向量。不同模型使用不同的分词器（tokenizer）类定义token。
特殊token：分隔符、结束符、开始符。
控制大模型生成文本的多样性参数：

  • 温度temperature：在模型计算出下一个token所有可能的概率分布后，temperature调整分布的平滑度。高温度会让低概率的token更容易选中，更具创造性但是会不稳。
  • Top P核采样：它设定一个概率阈值（P），然后从高到低累加所有token的概率，直到总和超过P为止。模型只会在这个累加出来的核心词汇表中选择下一个token。Top P越大候选词汇表越大。

大语言模型中的超能力

  • 联网搜索
    LLM会根据用户提问涉及的咨询自动调用搜索工具Tool，并将问题转化为多个简洁的搜索关键词。接着程序调用搜索引擎API获取信息，将该信息作为上下文提供给模型。
  • 读取文件：将不同格式的信息翻译成结构化的文本
    • pdf
    • word/excel
    • 图片
    • 音频/视频
  • 记忆能力
    • LLM本身无状态，每次对话都是全新互动，
      • 短期记忆：为了记忆系统会在每次对话时将最近几轮的问答作为上下文信息拼接到新提示词中发给模型。
      • 长期记忆：将信息存到数据库，使用时系统从数据库中读取信息并给模型。

API使用

API调用的是部署在云端的远程模型，而非自己电脑里的大模型。API Key是你的身份凭证，相当于门禁卡，需在代码中配置且不可泄漏；流式输出（streaming）让回答像打字机逐字呈现。

MCP：model context protocol,开放协议标准，目的是标准化LLM与外部数据源、工具及服务之间的交互方式。

function call与MCP区别

维度 function call MCP
定位 模型厂商私有接口（OpenAI，Qwen） 开放协议类似HTTP/USB-C
扩展性 需为每个模型单独适配 一次开发，多模型兼容
复杂性 适合简单、单次调用任务 支持多轮对话（复杂上下文管理）
生态依赖 依赖特定模型（gpt-4） 跨模型、跨平台（claude、cursor）
安全性 依赖云端API密钥 支持本地化数据控制
性质 功能 协议
范围 特定场景（单一数据源与功能） 通用（多数据源、多功能）
目标 扩展模型能力 统一接口，实现互操作
  1. 架构与组件
    MCP采用客户端-服务器（Client-Server）架构，核心组件：
    • MCP Host：运行AI模型的环境，如Claude Desktop、Cursor IDE
    • MCP Client：嵌入在Host中的组件，负责发起请求并与MCP Server通信
    • MCP Server：轻量级服务，提供特定功能（查询、API调用），供AI模型调用
  2. 核心功能：
    • Resources（知识扩展）：提供结构化数据（数据库、文档）以增强AI上下文理解
    • Tools（工具调用）：允许AI执行外部操作（发送邮件、查询Git、调用智能合约）
    • Prompts（提示模版）：预定义的指令模版，优化AI的任务执行

高并发内存瓶颈

KV Cache提升效率，将上一轮计算使用的KV放入缓存，下一轮计算直接使用上一轮KV，以及计算本轮KV。

  • 瓶颈1：内部碎片（请求空间多了），外部碎片（请求内存不连续的区域）
  • 瓶颈2:动态长度导致
  • 瓶颈3:Copy-on-Decoding开销，例如beam search(每次搜索多个而不是一个)
    pageAttention:
    内存分成许多block,用block表管理和维护。每个block可存16个token。block表记录了block块的索引。
  • 按需分配：用多少token分配多少个block。
  • 写时复制：各样本公用一些块，同时每个样本有自己私有的块。
  • 动态重排：不需要连续空间，有离散空间也可以用。

vLLM架构详解

推测解码

传统解码：一个一个token输出
推测解码：小模型（Draft model）一次输出多个token，大模型(Target model)给生成的token打分，大于阈值接收否则修改，大模型对拒绝的token生成候选token然后思索后给出最终token。打分过程快，思索过程慢。

MEDUSA推理框架

像美杜莎多头一样，每次预测多个token。
贪心算法只顾当前节点得分最高，不管整个路径中的得分最高。
Beam search保留多个路径，找路径中得分最高的路径。

Typical acceptance: 概率接收，超参temperature。

不再需要Draft Model (小模型),不用大模型打分。

EAGLE推理框架

增加了特征提取层，提取token特征向量比直接用token ID有更好的预测。包含草稿阶段和大模型验证阶段。token vector + token ID共同预测。

增大大模型接收的概率提升推理速度。

  • 做什么：基于生成的内容，逐个预测下一个token（自回归生成–之前的历史token生成当前一个token）
  • 计算特点：内存带宽密集型：每一步只计算一个token，瓶颈在读取KV Cache，GPU计算单元大量空闲。
  • 关键指标：TPOT（Time Per Output Token）
  • 资源需求：大显存，高内存带宽

SGLang系统中的RadixAttention

一种用于高效重用LLM推理过程中的KV Cache的方法。

  • 基数树（Radix Tree）：分节点（前缀）、分类存储KV值
  • LRU（最近最少使用）逐出策略：优先逐出最久未使用的缓存条目。
  • 缓存感知调度：合理调度编排提升缓存命中率，优先处理前缀匹配更长的请求。
